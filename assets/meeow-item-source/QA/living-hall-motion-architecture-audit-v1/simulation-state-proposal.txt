Living Hall spatial/motion architecture audit V1 — proposed local state

Current state has persistent logical mapRoom/mapPoint, statusActivity.posture, presence/Away/form and scene/event data, but no continuous motion coordinates. Proposed future PROGRAM-owned state is an ephemeral per-active-Hall map keyed by residentId:

{ hallId, roomId, mapVersion, foot:{x,y}, destination:{poiId,slotId,x,y}|null,
  segment/path, locomotion:'idle'|'walking'|'settling', facing, pose,
  behaviorId, startedAt, expectedEndAt, authorityToken }

This is a design sketch, not a schema change. Store only fields needed to resume an in-session interpolation and reject stale work. The existing resident record remains authority for hallId, physical presence/form, accepted status, logical mapPoint and current item/scene event. Local motion is lower priority and must consult those fields before every new behavior decision. The render view projects foot position; it never edits status prose or relationship state. BehaviorId/authorityToken is needed for cancellation when Status, Away, Active Social Presence or user-directed scenes assert new location.

For MVP one resident/two living-rug points, path can be a single legal segment. Do not duplicate world relationship, item, or social history in motion state. When metadata/version is invalid, stop and use a safe authored spawn/POI rather than improvising a coordinate. Human form or Away/Curator occupants do not enter Hall cat motion state.
