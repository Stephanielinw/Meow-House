Living Hall spatial/motion architecture audit V1 — position authority

Evidence: js/meeow-map.js:1-116; index.html:11303-11476, 20419-20467, 26146-26231, 28520-28524.

Resident save state can carry mapRoom, mapPoint, mapSpot, mapFurniture and mapPositionLabel. These are logical location/presentation fields; there is no persisted continuous Hall x/y, path, velocity, collision footprint, destination reservation or per-Hall coordinate. statusActivity.posture is persisted and chooses a rendered pose. The selected map tab is a UI choice, not resident location.

Position precedence on render: valid explicit mapPoint; else semantic inference from status/furniture/label; else mapSpot/mapRoom; else a stable hall+resident+room hash. getMapPlacement converts a chosen point anchor or region offset from 1024 coordinates to percentage CSS left/top. The room metadata supplies 10 dorm, 10 living, and 15 dining points. For a region, an eight-entry offset pattern spreads residents with the same logical point. For a fixed anchor, indices wrap when the anchor list is exhausted. Thus two cats can share one exact visual coordinate; no occupancy or collision gate exists.

The current location is Hall-linked by resident hallId plus one common room namespace; it is not a unique art/map instance for each Hall. Placement is presentationally spatial and derived during render, while the logical point may persist. The pose affects image anchor/height but does not choose coordinates. Current destinations exist only as named semantic points selected in Status Sync, not as traversable routes. Active Social Presence can temporarily write a chosen mapPoint with a fingerprint/return snapshot (index.html:22930-23211), another reason future local motion needs explicit preemption.

Answer: persistent coordinates NO; persistent logical place YES; collision/walkability NO; continuous locally selected destination NO.
