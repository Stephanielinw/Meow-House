SUMMARY
- PARTIAL system: 10 fixed Gregorian dates + 10 fixed lunar month/day entries + computed lunar New Year's Eve = 21 active holiday rules. User and resident birthdays are additional special dates, not holidays. A second four-date Gregorian prompt list is a subset, not four more presentation holidays.
- Primary detector: index.html checkSpecialEvent() ~13804-13839. Called at mount ~29195 and within checkDailyInitialization() ~25512 (also on visibility return). It writes reactive todayEvent and todayEventContext, not a durable holiday record.
- Calendar source: browser local Date shifted back 3 hours to match the local 03:00 operational-day boundary. Lunar conversion comes from remote lunar-javascript classic script in index.html:22. No bundled/local fallback was found.
- Mid-Autumn is configured as lunar 8-15. On 2026-09-25 after 03:00 America/Los_Angeles, a loaded working Lunar.fromDate should match and set todayEvent='中秋节快乐'. The user's observation was after an open/reload later that day, so live-midnight staleness alone cannot explain that report.
- The visible effect is very small: a prefix in the Hall guardian/Alfred message on mount, and on a successful Hall status refresh. enterHall() overwrites that message with generic cached/arrival copy before a refresh; failed/skipped/no refresh leaves no holiday text. No dedicated calendar banner, decoration, theme, particles, seasonal overlay, or automatic holiday modal exists in current code.
- The remote Lunar global is used inside an empty catch. If CDN loading/conversion fails, lunarMonth remains 0 and every lunar holiday quietly disappears while Gregorian holidays still work. Past browser network/load evidence is unavailable; this is a second possible failure, not proven as the incident cause.
